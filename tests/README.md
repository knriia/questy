Тесты регистрации пользователя охватывают `user`, `auth`, UoW и HTTP `/auth/register`.
Тестовые реализации находятся в `tests/fakes`, вспомогательный код — в `tests/support`.

Unit-тесты отдельных компонентов (локально):

```bash
make test-unit
```

Интеграционные тесты без БД: связка `AuthService` и `UserService`, HTTP-регистрация (локально):

```bash
make test-integration-no-db
```

Интеграционные тесты с PostgreSQL (через контейнер, нужны запущенные `app` и `postgres`):

```bash
make test-integration-db
```

Каждый тест отмечен одним из маркеров `unit`, `integration_no_db`, `integration_db`.
Все тесты без БД можно запустить через `.venv/bin/pytest -q -m "not integration_db"`.

GitHub Actions запускает CI при push и pull request. В отдельной проверке
выполняется `pre-commit run --all-files`: нарушения и изменения файлов хуками
завершают проверку ошибкой. Другая проверка запускает все три группы тестов
и проверяет их суммарное покрытие строк и веток всего `src`. Минимум задаётся через
`[tool.coverage.report].fail_under` в `pyproject.toml` (сейчас 56,38%).
Ошибка теста или покрытие ниже порога завершают CI ошибкой.
Для каждого запуска CI поднимается свой PostgreSQL 18, создаётся обычная тестовая
роль с `CREATEDB` и формируется `.env.test` с временными тестовыми значениями.

Покрытие измеряют `pytest-cov` и Coverage.py; измерение веток включено через
`[tool.coverage.run].branch = true`. Текущий результат: строки — 57,12%,
ветки — 38,64%, общий показатель строк и веток — 56,38%.
CI проверяет общий показатель, а отдельные значения доступны в JSON-отчёте.
HTML-, XML- и JSON-отчёты доступны в артефакте `coverage-reports` запуска CI.

Локальный запуск всех тестов с покрытием:

```bash
make test-coverage
```

Нужны запущенные `app` и `postgres`. Отчёты создаются в `htmlcov/`:
откройте `htmlcov/index.html`, чтобы увидеть непокрытые строки и ветки.
Эта команда также завершается ошибкой при покрытии ниже установленного порога.

Перед интеграционным прогоном скопируйте `.env.test.example` в `.env.test` и задайте
настройки тестовой роли PostgreSQL. `.env.test` исключён из Git.

Один раз создайте тестовую роль в запущенном PostgreSQL проекта:

```bash
make prepare-test-db
```

Команда читает `DB_USER` и `DB_PASSWORD` только из `.env.test` и создаёт роль
с правом `CREATEDB`, без прав суперпользователя. Для создания используется
администратор внутри контейнера PostgreSQL; тестам его настройки не передаются.
Если роль уже существует, команда завершится ошибкой, не меняя её пароль или права.

Контейнер собирается в `tests/di.py` без аргументов и конструкторов провайдеров.
Провайдер создаёт общий `Settings` с явным `_env_file`, указывающим на `.env.test`.
Рабочий `.env` при этом не читается. Переменные окружения имеют обычный приоритет
над значениями файла, поэтому тесты запускаются в отдельном процессе или контейнере
без рабочих переменных. В CI сформируйте `.env.test` с тестовыми настройками.

Провайдер БД явно содержит `engine`, `session_factory` и `session`.
Фикстура `test_container` создаёт тестовую БД и выполняет миграции перед тестами,
а после прогона закрывает engine и контейнер и удаляет БД.
Сессии закрываются при выходе из области запроса.

Запускайте тесты в окружении, из которого доступен тестовый `DB_HOST`.
`DB_NAME` — имя создаваемой тестовой БД. Для её создания используется стандартная
служебная БД `postgres`. Тестовая роль должна иметь право `CREATE DATABASE`, доступ к служебной БД
и не иметь доступа к рабочей БД. Конфиг не создаёт роль и не меняет её права.

В существующем PostgreSQL создаётся база с именем `DB_NAME` из `.env.test`.
Движок подключается к ней через `Settings.db_url`; отдельного метода DI для URL нет.

База создаётся один раз на прогон. В ней выполняется `alembic upgrade head` через
миграции проекта, без `metadata.create_all`. Между тестами очищаются пользователи
и связанные записи. После прогона временная база удаляется, включая случай ошибки
миграции или теста. Если БД уже существует, запуск завершается ошибкой без её удаления.
Одновременно запускается только один прогон с этим именем БД.
